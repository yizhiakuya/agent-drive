# 项目架构师

当用户询问"项目怎么设计/怎么维护"、要求审查现有代码架构、或要重构/拆分模块时，使用本技能。

## 核心立场

> 好的架构不是一次设计出来的，是通过**持续解耦**养出来的：每个文件一句话能说清职责，每个改动都小而可验证，每次回归都全绿。

架构的敌人是"上帝文件"——一个文件塞了多类职责，改 bug 改两处，加功能先考古。

## 一、设计原则（按优先级）

1. **单一职责**：一个文件/类/函数只做一件事。判断标准：能否用一句话（不含"和"）说清它的职责？
2. **单向依赖**：上层依赖下层，下层绝不依赖上层。画依赖图，发现环立即拆。
3. **依赖注入**：对象在组装点（Container）显式组装，禁止模块级全局单例和隐式状态。
4. **接口隔离**：调用方只依赖协议/接口，不依赖具体实现（业务不 import 具体 Provider/Storage 类）。
5. **显式优于隐式**：配置、参数、依赖都要看得见；魔法值进配置文件。
6. **每步可运行**：重构的每一步之后项目都能跑、测试都绿，不搞"大爆炸"式重写。

## 二、分层架构模板（FastAPI + React + Agent 系统）

```
表现层     React 组件          → 只做渲染和交互
接口层     api/v1 路由 + schemas → 协议转换/参数校验/版本管理，无业务
应用层     services/           → 用例编排/事务边界/跨领域协调
领域层     agent/ llm/ storage/ ingest/ → 核心业务，不依赖 HTTP/框架
基础设施   core/ db/ queue/    → config/logging/errors/container/retry
```

检查清单：
- [ ] 路由文件里没有业务逻辑（只有参数校验 + 调 service）
- [ ] 领域模块不 import fastapi / flask（框架无关）
- [ ] 所有外部依赖通过协议注入（可测试替身）
- [ ] 版本化 API（/api/v1/*），破坏性变更升版本

## 三、维护方法论：上帝文件体检与解耦

### 3.1 体检（找到耦合）
```bash
# 找大文件
wc -l $(find . -name "*.py" | grep -v __pycache__) | sort -rn | head -10
# 列职责清单：一个文件里的函数/类越多越危险
grep -n "^def \|^class \|^    def " <file>
```
判定：>300 行或 >5 类职责（提示词/上下文/执行/解析/持久化混在一起）→ 需要拆分。

### 3.2 拆分流程（五步法）
1. **列职责**：把文件里所有函数按职责分组（提示词工程/上下文管理/执行引擎/...）
2. **拆新文件**：每组职责一个文件，命名 = 职责名（prompt.py / context.py / confirm.py）
3. **消除重复**：两份相似逻辑（如 run/run_stream）合并为统一核心 + 两个薄入口
4. **跑回归**：单元 + 集成 + 端到端全绿后才算完成
5. **更新文档**：架构文档同步，git 单独提交（refactor: 前缀）

### 3.3 消除重复的通用模式
```
重复:  fn_a() { 核心逻辑 X }    fn_b() { 核心逻辑 X 的复制 }
解法:  _core() 统一生成器/函数 → fn_a = 聚合(_core) / fn_b = 透传(_core)
```
判断重复：改 bug 需要改几处？>1 处 = 有重复。

## 四、测试策略（四层）

| 层 | 工具 | 测什么 | 例子 |
|----|------|--------|------|
| 单元-脚本 | python3 直跑 | 核心逻辑快速回归 | test_retry 重试退避 |
| 单元-pytest | pytest | 断言丰富的功能 | 集成 API TestClient |
| 集成 | TestClient + 临时目录容器 | 路由/组装/持久化 | test_api 6 项 |
| 基准 | 真实 LLM | 可靠性/一致性 | benchmark_real ×3 |

规则：**改架构必跑全量回归；新增能力必须带测试；测试用临时目录隔离数据。**

## 五、工程化底线

- Makefile 提供 install/dev/test/bench/build 入口
- pyproject.toml 声明依赖和 pytest 配置
- .env.example 文档化全部环境变量（敏感信息绝不入库）
- git：功能/修复/重构分开提交；commit message 写"为什么"不只"是什么"
- 提交前安全扫描：`git diff --cached | grep -iE "sk-|api_key"`（API key 零容忍）

## 六、实战案例：loop.py 解耦（本项目真实案例）

**问题**：433 行塞了 8 类职责（提示词工程/上下文管理/token 估算/JSON 解析/技能注册/非流式/流式/会话摘要），run() 和 run_stream() 重复 150 行。

**解法**：
```
拆分前:  loop.py (433行, 8职责)
拆分后:  loop.py    294行  纯编排引擎（_execute 统一生成器）
         prompt.py   75行  提示词工程
         context.py  38行  上下文管理
         confirm.py  18行  确认判定
```
**效果**：重复代码清零（run=聚合事件 / run_stream=透传事件），改一处两入口生效；每文件一句话可说清职责。

## 七、与 Agent 开发的关系

本技能与 agents-best-practices（agent harness 设计）互补：
- **本技能**：软件项目的架构与维护（文件组织/依赖/重构）
- **agents-best-practices**：agent 运行时本身怎么设计（loop/工具/权限）
Agent 项目的架构同时适用两者：项目骨架用本技能，agent 内部机制用 agents-best-practices。
