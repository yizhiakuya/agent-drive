> 来源：Anthropic《Building Effective Agents》· Princeton arXiv 2602.16666《Towards a Science of AI Agent Reliability》· app.build《Six Principles for Production AI Agents》·《AI Agent 开发实战》

## 一、什么是 Agent（本质定义）

**Agent = 大脑(LLM) + 手脚(Tools) + 记忆(Memory) + 主见(Autonomy) + 护栏(Guardrails)**

- **大脑**：负责思考与决策（LLM）
- **手脚**：负责执行（工具）
- **记忆**：短期=对话上下文，长期=跨会话知识
- **主见**：自主推进任务，而非"你说一步它动一步" ← Chatbot 与 Agent 的分水岭
- **护栏**：预算/权限/审批/审计/沙箱 ← 决定 Agent 能否上线

**一句话定义**：给它一个目标、一个工具箱和一套边界，它在循环里推进任务，直到完成或停下。

## 二、好 Agent 的四个可靠性维度（Princeton 框架）

| 维度 | 含义 | 在 Agent Drive 的落地 |
|------|------|----------------------|
| **Consistency 一致性** | 同一任务多次运行，行为与结果稳定 | 相同指令不应产生互相矛盾的操作；工具执行确定性 |
| **Robustness 鲁棒性** | 抗扰动：输入措辞变化、文件环境变化都能正确处理 | 语义搜索不依赖精确文件名；空目录/大文件/特殊字符文件都能处理 |
| **Predictability 可预测性** | 失败模式是固定、可识别、可调试的 | 错误分类清晰（工具缺失/权限不足/LLM 超时），而非随机失败 |
| **Safety 安全性** | 错误有界，不造成不可逆伤害 | 删除需确认、写前快照、路径穿越防护、成本步数上限 |

> ⚠️ 关键洞察：**能力 ≠ 可靠性**。准确率高的模型可能不可靠；重要的是"在操作包络内稳定工作，失败时优雅降级"。

## 三、生产级 Agent 六大工程原则（app.build）

1. **系统提示 = API 文档**：直接、详细、清晰、无矛盾。工具要写清楚：完整用法、每个参数含义/类型/格式、预期输出格式、前置条件和错误情况。
2. **拆分上下文**：默认只给最少必要知识，通过工具按需获取更多。警惕"注意力衰减"。
3. **精心设计工具**：
   - 粒度一致（不混用 `read_byte` 和 `deploy_to_kubernetes`）
   - 数量少：核心工具 < 10 个，每工具 1-3 个严格类型参数
   - **幂等性**：重复执行结果一致（简化状态管理与错误恢复）
   - 无重叠、无歧义
4. **反馈循环（Actor-Critic）**：LLM 生成 → 程序验证。Critic 做编译/测试/不变量检查，过滤错误输出。
5. **LLM 驱动错误分析**：失败日志喂给 meta-agent 分析根因，反哺系统提示/工具/上下文。
6. **沮丧行为 = 系统问题信号**：Agent 犯傻先调试系统（工具缺失/提示模糊/上下文不足），再怪模型。

## 四、Agent Drive 主 Agent 规格

### 4.1 角色
**File Concierge（文件管家）**：用户数字生活的管家。所有文件是"知识资产"——理解、组织、关联、随时取用。

### 4.2 能力边界（M1→M2 演进）
```
L0 对话与自管理 ✅      L1 文件理解 ✅          L2 主动服务 ✅(部分)
├─ 对话                  ├─ PDF/图片理解 ✅      ├─ 定时整理 ✅(规则自动执行 03:30)
├─ 搜索/读取/组织文件 ✅  ├─ 语义搜索 ✅          ├─ 规则自动执行 ✅
├─ 自管理配置 ✅         ├─ 全文检索 ✅          ├─ 知识图谱问答 ⏳(M4 候选)
└─ 偏好/规则记忆 ✅       └─ 文件关系 ⏳(M4 候选)  └─ 主动提醒 ✅(主动汇报卡片)

（音视频理解：播放 ✅ / 转写 ⏳ 未做——见 docs/android.md §五 与 architecture.md 扩展点）
```

### 4.3 工具设计规范（ACI）
- 核心公开工具保持少量、粒度一致；业务能力统一收敛到 `backend_api`，避免为每个 REST 路由重复设计 Agent 包装层。
- `backend_api` 只有稳定的 discover/call 外壳参数；HTTP operation 的 path/query/body/file 参数由 OpenAPI Schema 按需发现，调用前必须先 discover；未暴露 HTTP 的既有能力使用同一 envelope 的 `INTERNAL name` 兼容 operation。
- HTTP operation 使用 `METHOD /api/v1/path` 稳定标识，兼容 operation 使用 `INTERNAL name`；HTTP 调用由 FastAPI 路由再次执行类型、路径和权限校验。
- 工具文档含：发现流程、参数语义、输出格式、前置条件、错误情况；结果统一结构化并截断/脱敏。
- 安全分级按实际 operation 动态计算：🟢查询自动 / 🟡低风险内部整理 / 🔴写入和破坏性操作确认。

### 4.4 循环设计（Actor-Critic）
```
Actor(LLM): 理解意图 → 规划 → 调工具 → 观察
    ↓
Critic(程序): 工具执行后验证
    ├─ 参数合法性（路径安全、类型）
    ├─ 操作结果校验（rename 后目标存在？）
    ├─ 业务不变量（文件系统层级、配置 JSON 合法）
    └─ 成本/步数护栏
    ↓
失败 → 结构化错误 → Agent 可读 → 重试或优雅降级
```

### 4.5 记忆分层
| 层 | 内容 | 存储 |
|----|------|------|
| L1 会话 | 当前对话上下文 | 前端 history（截断策略） |
| L2 偏好 | 语言/整理风格/命名规则 | `memory.json` ✅ |
| L3 文件 | 摘要/实体/标签/向量/关系 | M2 pgvector+图谱 |

### 4.6 失败哲学
- **优雅失败**：LLM 不可用时给出明确引导；工具失败返回结构化错误而非崩溃
- **可调试**：审计日志 + 工具轨迹 + 错误分类
- **先调试系统**：Agent 异常 → 查工具/提示/上下文
